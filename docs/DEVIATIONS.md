# DEVIATIONS.md — where S01 differs from the design documents

Each deviation was accepted up front because the build environment differs from the documents' assumptions.

| # | Document says | What S01 does | Why | Effect on later stories |
|---|---|---|---|---|
| 1 | `STACK.md` 15, `ARCHITECTURE.md` Environments: local database is Postgres 18 in Docker Compose | `docker-compose.yml` (Postgres 18) is committed and `make db-up` uses it when a Docker daemon answers. With no daemon, `make db-up` creates one database per worktree (`qrypt_<dirname>`) on a local Postgres 16 server (`LOCAL_PG_ADMIN_URL`, default `postgresql://dev:dev@localhost:5432/postgres`). `DATABASE_URL` in the environment or on the command line overrides both | No Docker daemon in the build sandbox; a Postgres 16 server is running | Tests ran on Postgres 16 here. Nothing in the schema needs 18-only features, but the Compose path and Postgres 18 are unexercised until a machine with Docker (or CI, which uses the `postgres:18` service) runs it |
| 2 | AC6 / AC7: empty Render Postgres, `make spike-roles` on Render | Script and Makefile target delivered and run against the local Postgres 16 | No Render account | AC7 stays unverified on Render. If the real run fails, `STACK.md` 19 says to fall back to Neon |
| 3 | AC3 / AC4 / AC5 (deployed): live TLS URL | `render.yaml` delivered; routes verified locally through the HTTP test client and a local uvicorn | No Render account | Deployment, TLS and the http-to-https refusal are unverified; see `docs/DEPLOY.md` for the exact commands to run |
| 4 | AC9: the gate runs on GitHub | `.github/workflows/gate.yml` delivered | No GitHub Actions run is possible from the sandbox | Unverified until the branch is pushed |
| 5 | `STACK.md` 17 / CP-1: gitleaks CLI | `tools/secret_scan.py` runs gitleaks when it is on `PATH` and otherwise a regex scanner over the working tree and the full git history (AWS keys, private-key headers, provider tokens, high-entropy secret assignments, passwords in URLs). CI installs the gitleaks CLI | The gitleaks release download is blocked by the sandbox proxy and the tool is not on PyPI | The fallback is coarser than gitleaks (fewer rules); CI uses the real tool |
| 6 | AC8 "a stub tool-call p95 check" | The p95 is measured over 1,000 stub calls through the MCP SDK's in-memory client (real tool handlers, authentication and result building; no process pipe) | Keeps the gate fast and independent of process start-up | The PF-1 measurement over stdio belongs to S36 |
| 7 | AC1 "the human also opens MCP Inspector" | The snippet is `docs/mcp-client.json`; `make mcp-list` drives the same stdio server with the SDK client. Inspector itself was not run (it needs a network fetch of the npm package) | Sandbox | The human demo performs the Inspector step; the snippet has a placeholder directory to replace |
| 8 | AC1 "fixed stub client key in its environment" | The key is the literal `stub-client-key` (admin: `stub-admin-key`), committed in tests and `docs/mcp-client.json`. These are not secrets | Story calls for two fixed test keys | S05 and S06 replace them with hashed credentials |
| 9 | `ARCHITECTURE.md` Database roles: `migrator` owns every table | S02 creates the `migrator` role but does not change table ownership; the role running the migration owns the tables (the superuser locally) | Reassigning ownership needs membership of `migrator`, which a managed Postgres admin may not have | Grants and guards behave the same. Grant tests use the connecting admin as the migrator |
| 10 | S01 deviation 8: the stub keys are accepted by the skeleton | After S05 a key authenticates only if a `credentials` row hashes to it under `KEY_HASH_SECRET`. The suite inserts rows for the two test keys (`tests/conftest.py`); server subprocesses in tests and `make mcp-list` need `DATABASE_URL` and `KEY_HASH_SECRET` in the environment | Access is real (S05) | `make mcp-list` / `mcp-call` need a credential row for the key used until the seed script (S17) creates them |
| 11 | S04 AC1/AC4 evidence: `docker compose restart db` | The always-on gate case kills the test database's own backends with `pg_terminate_backend` and checks the next read runs on a new backend pid. The real restart (`service postgresql restart`, asserting `pg_postmaster_start_time()` changed) is opt-in: `make test-db-restart` (`ALLOW_DB_RESTART=1`), skipped otherwise. AC2/AC3 simulate a stopped database with an unreachable address | No Docker daemon; the local server is shared with other worktrees, so a restart in every gate would disrupt them | The Compose restart is unexercised until a machine with Docker runs it |
| 12 | AC2 "at 2.0 to 2.2 s" vs AC6 and RL-1 "within 2 s" | Retired (S20): a take waits `WAIT_S` = 1.8 s and the error is out in under 2.0 s, which satisfies RL-1 and the AC2 window's intent | Orchestrator decision | S11 and S20 tests assert 1.8 s to under 2.0 s |
| 13 | AZ-6: failed redemptions for one owner are limited; the lock-out cost is accepted | Implemented as written (S22). Residual risk, flagged for the human: anyone holding a client key who knows an owner id can send 5 wrong attempts every 10 minutes and keep that owner locked out indefinitely; the limit is per owner, not per caller. Also, attempts for one owner queue behind a per-owner lock for at most `RATE_LIMIT_LOCK_TIMEOUT_MS` (2 s) and then get 503 `temporarily_unavailable`, so a flood for one owner cannot hold database connections | AZ-6 accepts the lock-out; the timeout keeps the serialisation from becoming a denial of service on the pool | Nothing to build; a per-caller limit or alerting on `rate_limited` counts would need a new requirement |
| 13 | S31 AC4 and `STACK.md` 7: the dump is made in a Postgres 18 container and restored into a fresh Postgres 18 | `scripts/backup.py` runs whatever `pg_dump` is on `PATH`; here that is the Postgres 16 client against the local Postgres 16 server, and `make restore-drill` restores into a throwaway local Postgres 16 cluster (new `initdb`, so none of our roles exist in it). `DRILL_ADMIN_URL` points the drill at any fresh server (a `postgres:18` container). The workflow installs `postgresql-client-18` | No Docker daemon and no Postgres 18 in the sandbox | The Postgres 18 dump and restore are unexercised until CI or a machine with Docker runs them. The backup workflow, the real key pair and the artifact upload (E1/E4) have never run |
| 14 | S31 AC4 "restores it and re-runs the migrations" | The drill reads the dump's `alembic_version`, runs the migrations up to that revision on the empty database (roles, grants, triggers), loads only the dump's data (`age -d \| pg_restore --data-only --disable-triggers`, no plaintext file), then migrates to head. It does not replay the schema stored in the dump | Roles and grants are not in a dump (`--no-privileges`); migrations are their source of truth | A schema change made outside the migrations would not come back. A dump older than the code is brought to head after its data is loaded (tested with a dump at `s02_dbpolicy`) |
| 15 | S31 migration `s31_backup_version` | `backup` is granted SELECT on `alembic_version`, which the role grants table of `ARCHITECTURE.md` does not list | `pg_dump` locks and dumps every table and fails without it | None; the table holds one revision id |
| 14 | S20 AC4: a `get_random_bytes` call names "a batches row of 64 KiB or more" | The pool serves the startup check's 1 KiB (S12: those bytes join the pool) after every refill batch, so once the first 64 KiB refill has landed a value always names a 64 KiB batch. Before it lands (a few ms after start) a call is served from the 1 KiB check batch, whose row says `kib = 1` | Served in arrival order, the first 1,024 bytes after every start would name the 1 KiB check, and AC4 could not hold on a fresh server | S10 and S12 tests are unchanged; `Pool.add(..., last=True)` is the only new behaviour |
| 15 | S20 AC9: a live run against Qrypt with a real token | Not run. `docs/DEPLOY.md` has the exact procedure and a budget log to fill in; `make demo-issue` prints the same two queries against the mock | No Qrypt token here | AC9 stays a human step |
| 16 | S20: "make the MCP server start the pool" | The startup check runs in the server's lifespan, which waits for it at most `STARTUP_WAIT_S` (5 s); a slower check (a 429 backoff can last minutes) finishes in the background, and calls meanwhile wait on the pool's own bound. `initialize` is therefore never held more than 5 s | The check must start before the first call (DE-5) and Inspector gives up at about 10 s | None |
| 17 | S33: "owner user-42" for every demo step | `make demo-redeem` issues the expiry case to user-43 and the lock-out case to user-77, so the lock-out and the repeated mock bytes do not disturb the other steps. The lock-out (any caller who knows an owner's name can lock that owner out for the window) is the known residual risk shown in AC5 | The mock Qrypt returns the same bytes in each new process; the lock-out is by design (AZ-3) | None |
